Before writing any code, it was a small journey to figure out my way around STM32CubeIDE, a set of tools much less "code and press run" than that of the Arduino, Raspberry Pi, ESP32, etc. The less abstracted environment does make it more clear what is going on behind the scenes of those other development environments. There were many misconceptions that I had to sort out, such as believing that the STM32F7 firmware package provided by ST is something meant to live on the board/chip semi-permanently, like an EEPROM; it is not that, rather "firmware" refers to the development package that is needed to *build* firmware for the microcontroller, and includes the HAL, middleware, and since I'm using a board with external accessories, a BSP.

One learning moment came from dealing with access protection on the physical address space. In order to manage the speculative instruction prefetcher, CubeMX creates a protected region in memory that prevents the prefetcher from reading the addresses associated with disconnected external memory and peripherals; otherwise, the prefetcher may attempt to read and execute those unusable regions as instructions, which would result in a bus fault. Enabling and connecting those peripherals (in this case, SDRAM) doesn't automatically un-block the addresses, and the protected region is hard-coded in CubeMX. Claude suggested using user-created code to patch the region during initialization, immediately after it was created in the first place. However, with manual research, I found out that the intended solution is to create higher-priority protected regions that overlap with the main one and enable read/write/executes. Claude had actually done that before for another sub-region, but didn't "think" to do that for this one.
